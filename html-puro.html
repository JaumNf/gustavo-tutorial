Fundamentos

Os conceitos que organizam todo o resto. Sem isso, os nomes de framework viram sopa de letrinha.

Front-end vs Back-end

Revisão

Front-end é tudo que roda no navegador do visitante: o que ele vê, lê e clica. Back-end é o que roda no servidor, invisível para ele: banco de dados, login, envio de e-mail, processamento de pagamento.

O exemplo que fecha a ideia é uma loja online. A vitrine com fotos, o carrinho que você vê na tela e o botão “comprar” são front-end. Quando você clica em comprar, quem confere estoque, calcula frete, cobra o cartão e grava o pedido é o back-end.

PerguntaFront-endBack-end
Onde roda?No navegador do visitanteNo servidor
O visitante vê o código?Sim — é só abrir o “ver fonte”Não, nunca
Linguagens típicasHTML, CSS, JavaScriptJavaScript (Node), Python, PHP, Java, Ruby
Guarda dados?Não de forma confiávelSim — é a função dele
Seus projetos usam?Sim, integralmenteNão — a conversão vai pro WhatsApp
Por que isso importa pra você: como sua landing page não tem back-end, nada que exija segredo pode estar nela. Uma chave de API escrita no seu HTML está pública para qualquer visitante. Se um dia precisar de algo assim, esse é exatamente o momento em que entra um back-end.

UI vs UX

Revisão

UI (User Interface) é o desenho: cores, tipografia, espaçamento, ícones, o formato do botão. UX (User Experience) é a experiência de usar: se a pessoa entende onde clicar, se o caminho até o objetivo é curto, se ela não fica perdida.

São independentes. Dá pra ter UI lindo com UX péssimo — um site premiado onde ninguém acha o telefone. E o contrário: uma página feia, sem graça, mas que resolve o problema da pessoa em dois cliques.

Numa landing page, a decisão mais cara costuma ser de UX, não de UI: quantos campos o formulário tem, se o botão de WhatsApp aparece antes ou depois da rolagem, se a pessoa precisa entender a oferta antes de agir. Cada campo a mais no formulário derruba conversão — isso é decisão de UX, e nenhuma escolha de cor conserta.

Frameworks e ecossistema

O mapa dos nomes que aparecem em toda vaga, tutorial e menu de ferramenta — e onde cada um se encaixa.

O que é framework (e o que é biblioteca)

Revisão

Framework é uma estrutura de código pronta que já resolve os problemas comuns de um tipo de projeto, para você não escrever tudo do zero.

A diferença para uma biblioteca está em quem manda no fluxo. Numa biblioteca, você chama ela quando precisa — uma função de formatar data, por exemplo; o controle é seu. Num framework, ele chama você: define a estrutura do projeto, as pastas, o ciclo de vida, e o seu código se encaixa nas regras dele.

Isso tem um nome clássico: inversão de controle. Biblioteca é ferramenta na sua mão. Framework é a oficina — você trabalha dentro dela.

O custo que ninguém menciona: framework economiza tempo no começo e cobra depois, em manutenção. Um projeto React de 2021 parado não “continua funcionando”: as dependências envelhecem, quebram entre si, e atualizar exige trabalho. Um HTML puro de 2015 abre hoje igual. Isso não é argumento contra frameworks — é o motivo de escolher um só quando ele paga o próprio custo.

Estão na mesma lista porque são destinos possíveis do código gerado, não porque sejam a mesma categoria de coisa.

Node.js — o runtime, não um framework

Revisão

Antes do Node, JavaScript só rodava dentro do navegador. O Node pegou o motor que o Chrome usa para executar JS (o V8) e passou a rodá-lo fora do navegador — no seu computador ou num servidor. Com isso, JavaScript virou uma linguagem que também serve para back-end.

Node não é framework: é o ambiente onde o código roda. A hierarquia fica assim:

hierarquia
JavaScript  ← a linguagem
   │
   ├── roda no navegador   →  front-end (React, Vue, ou JS puro)
   │
   └── roda no Node.js     →  back-end
                                 └── Express, NestJS, Fastify (frameworks)

Vale saber mesmo sem fazer back-end: quase toda ferramenta moderna de desenvolvimento roda sobre Node. Se um dia você instalar o Tailwind, um compilador de Sass ou um minificador, é o Node que executa essas ferramentas na sua máquina — mesmo que o site entregue não tenha uma linha de Node.

Quando sair do vanilla

Revisão

O gatilho não é o número de páginas. Sete páginas estáticas continuam sendo sete arquivos HTML. O gatilho é a origem do conteúdo e a existência de estado compartilhado.

árvore de decisão
O conteúdo muda sem você editar o código?
  ├── NÃO → HTML puro resolve. Mesmo com 20 páginas.
  └── SIM ↓

Precisa de login, banco de dados ou pagamento?
  ├── SIM → back-end + framework. Sem alternativa.
  └── NÃO ↓

É muito item repetido com o mesmo layout
(catálogo, blog, portfólio grande)?
  ├── SIM → gerador de site estático ou Next.js
  └── NÃO → HTML puro ainda ganha.

Sobre o caminho de migração: vanilla → React é reescrita, não upgrade. O React trabalha com componentes e estado, uma lógica diferente da manipulação direta do DOM; o CSS aproveita bastante, a lógica não. Já React → Next.js é tranquilo, porque um é construído sobre o outro: muda a organização de pastas e o roteamento, não a lógica dos componentes.

npm e package.json

Novo

npm (Node Package Manager) é o instalador de pacotes do mundo JavaScript. Você pede uma biblioteca pelo nome e ele baixa ela e tudo de que ela depende.

O package.json é a ficha do projeto: nome, versão, lista de dependências e atalhos de comando. É o arquivo que permite outra pessoa clonar seu projeto, rodar um comando e ter exatamente o mesmo ambiente.

terminal
npm init -y              # cria o package.json
npm install nome-do-pacote   # instala e anota na lista
npm run dev              # roda um atalho definido em "scripts"

A pasta node_modules que aparece guarda os pacotes baixados. Ela é gigante e nunca vai pro Git nem pro servidor — o package.json é que descreve o que precisa ser reinstalado.

No seu fluxo: entregando HTML único, você não usa npm no projeto do cliente. Mas vai encontrar npm em qualquer tutorial moderno, e é assim que você instalaria uma ferramenta de apoio — um minificador, por exemplo — na sua máquina.

Bundlers: Vite e Webpack

Novo

Um bundler (empacotador) pega dezenas de arquivos de código-fonte e produz poucos arquivos otimizados para o navegador: junta, remove o que não é usado, minifica, converte sintaxe nova para versões que navegadores antigos entendem.

Webpack é o veterano: poderoso, configurável e trabalhoso. Vite é a geração seguinte: praticamente sem configuração, com recarga instantânea durante o desenvolvimento. Hoje, projeto novo começa com Vite.

É aqui que mora a palavra build. “Precisa de build” significa: o código que você escreve não é o código que vai pro ar — existe uma etapa de processamento no meio.

Por que isso é relevante pra você: a maior vantagem da sua entrega é justamente não ter essa etapa. O arquivo que você escreve é o arquivo que roda. Isso elimina uma classe inteira de problema — configuração quebrada, versão incompatível, build que falha no servidor.

TypeScript

Novo JS

TypeScript é JavaScript com tipos declarados. Você diz que uma variável é texto ou número, e o editor avisa antes de rodar quando algo não bate.

comparação
// JavaScript — só descobre o erro rodando
function calcularFrete(peso) {
  return peso * 12.5;
}
calcularFrete("dois quilos");   // NaN, silenciosamente

// TypeScript — o editor acusa antes de rodar
function calcularFrete(peso: number): number {
  return peso * 12.5;
}
calcularFrete("dois quilos");   // erro apontado na hora

O navegador não entende TypeScript — ele é convertido para JavaScript antes de ir pro ar. Ou seja: exige build.

Compensa em projeto grande, com várias pessoas, onde um erro de tipo custa caro. Em landing page de uma página, o custo da etapa de build supera o benefício.

Hierarquia de títulos

Um <h1> por página — é o título principal, e o Google usa ele com peso. Os demais descem em ordem: h2 para seções, h3 para subseções. Não pule níveis para conseguir um tamanho de fonte: tamanho é trabalho do CSS, hierarquia é trabalho do HTML.

Regra prática: se você está prestes a escrever <div class="alguma-coisa">, pergunte se existe uma tag com esse nome. Muitas vezes existe — e ela vem com comportamento de teclado e significado de graça.

O <label> não é opcional

O for do label tem que bater com o id do campo. Isso faz o clique no texto focar o campo, permite o leitor de tela anunciar o rótulo, e aumenta a área de toque no celular. Usar só placeholder como rótulo é um erro: ele some quando a pessoa começa a digitar.

javascript
// Deixa o navegador validar; só depois monta a mensagem
form.addEventListener('submit', (e) => {
  e.preventDefault();
  if (!form.reportValidity()) return;   // mostra os erros nativos

  const d = new FormData(form);
  const msg = `Olá! Vim pelo site.\n\n`
            + `Nome: ${d.get('nome')}\n`
            + `Convidados: ${d.get('pessoas')}`;

  window.open(`https://wa.me/5567999999999?text=${encodeURIComponent(msg)}`,
              '_blank', 'noopener');
});
encodeURIComponent é obrigatório. Sem ele, acento, quebra de linha e o símbolo & quebram a URL do WhatsApp e a mensagem chega cortada.

Box model

Novo CSS

Todo elemento é uma caixa com quatro camadas, de dentro para fora: conteúdo, padding (espaço interno), border (borda) e margin (espaço externo).

as quatro camadas
┌─────────── margin ────────────┐   ← empurra os vizinhos
│  ┌──────── border ─────────┐  │
│  │  ┌───── padding ─────┐  │  │   ← afasta o conteúdo da borda
│  │  │                   │  │  │
│  │  │     conteúdo      │  │  │
│  │  │                   │  │  │
│  │  └───────────────────┘  │  │
│  └─────────────────────────┘  │
└───────────────────────────────┘

A linha que você sempre escreve (e por quê)

Por padrão, width: 300px define a largura só do conteúdo. Se você somar padding e borda, a caixa fica maior que 300px — e o layout estoura. O border-box muda isso: a largura passa a incluir padding e borda.

css
* { box-sizing: border-box; }

/* Agora isto ocupa exatamente 300px, não 340px: */
.card {
  width: 300px;
  padding: 20px;   /* 20px de cada lado */
}

Colapso de margem

Duas margens verticais que se encostam não somam — vence a maior. Margem de 30px embaixo de um elemento e 20px em cima do próximo resultam em 30px, não 50px. É a causa mais comum de “o espaçamento não está batendo”. Usar gap no flex ou grid evita o problema inteiro.

O DOM

Novo JS

Quando o navegador lê seu HTML, ele monta na memória uma árvore de objetos representando cada elemento. Essa árvore é o DOM (Document Object Model). O JavaScript não mexe no arquivo HTML — ele mexe nessa árvore, e o navegador redesenha a tela.

do arquivo à árvore
<body>                    document
  <header>                  └── html
    <h1>Art Bar</h1>             ├── head
  </header>                      └── body
  <main>                              ├── header
    <p>Drinks</p>                    │     └── h1 → "Art Bar"
  </main>                             └── main
</body>                                     └── p  → "Drinks"

Duas consequências práticas. Primeira: se o seu <script> roda antes do elemento existir na árvore, ele não acha nada — por isso o script vai no fim do <body>. Segunda: alterações no DOM são temporárias. Recarregou a página, voltou tudo ao HTML original.

IntersectionObserver

Novo JS

Avisa quando um elemento entra ou sai da tela, sem você ficar calculando posição no scroll. É a ferramenta certa para animação de entrada, contador que começa ao aparecer e menu que destaca a seção atual.

javascript
const observador = new IntersectionObserver((entradas) => {
  entradas.forEach(entrada => {
    if (entrada.isIntersecting) {
      entrada.target.classList.add('is-in');
      observador.unobserve(entrada.target);   // anima uma vez só
    }
  });
}, { threshold: .15 });   // 15% visível já conta

document.querySelectorAll('[data-reveal]')
  .forEach(el => observador.observe(el));

O threshold é a fração do elemento que precisa estar visível para disparar. O unobserve é o que impede a animação de repetir a cada rolagem — e libera memória.

Armadilha de SEO e de primeira impressão: se o CSS deixa o elemento em opacity: 0 esperando o observer, e o JS falha ou está desligado, o conteúdo nunca aparece. Deixe o estado final como padrão e aplique o inicial só quando o JS assumir — ou aceite que a seção pode ficar invisível para alguém.

O seletor :has()

Novo CSS

Durante vinte anos o CSS só olhava para baixo: você estilizava um filho, nunca o pai. O :has() inverte isso — estiliza um elemento com base no que existe dentro dele.

css
/* card que TEM imagem ganha layout diferente */
.card:has(img) {
  grid-template-columns: 120px 1fr;
}

/* campo preenchido: esconde o rótulo flutuante */
.campo:has(input:not(:placeholder-shown)) .rotulo {
  opacity: 0;
}

/* o formulário inteiro reage a um checkbox marcado */
form:has(#outro:checked) .campo-extra {
  display: block;
}

/* menu aberto trava a rolagem — sem tocar no JS */
body:has(.menu-painel.is-aberto) {
  overflow: hidden;
}

Aquele último exemplo merece atenção: é um caso em que você provavelmente escreve document.body.style.overflow = 'hidden' no JavaScript. Com :has(), o CSS reage sozinho à classe que já existe.

Nome informal: chamam de “seletor pai”, mas ele é mais que isso — funciona com irmãos também. .titulo:has(+ .subtitulo) estiliza um título só quando existe um subtítulo logo depois dele.

Container queries

Novo CSS

Media query pergunta “qual o tamanho da tela?”. Container query pergunta “qual o tamanho do espaço onde eu estou?”. A diferença é grande: o mesmo card pode aparecer largo numa seção e estreito numa barra lateral, e se adaptar sozinho aos dois.

css
/* 1. declara que este elemento é um container mensurável */
.coluna {
  container-type: inline-size;
  container-name: coluna;
}

/* 2. o filho reage à largura DA COLUNA, não da tela */
@container coluna (min-width: 420px) {
  .card {
    display: grid;
    grid-template-columns: 140px 1fr;
    gap: 16px;
  }
}

Por que isso muda o jeito de pensar: com media query, um componente precisa saber em que ponto da página ele foi colocado. Com container query, ele se vira sozinho em qualquer lugar. É o que torna um componente de verdade reutilizável.

Onde te ajuda hoje: naquela grade de cards que você monta com auto-fit. Quando a coluna fica estreita, o card pode empilhar foto e texto; quando fica larga, coloca lado a lado — sem você escolher breakpoint de tela nenhum.

@layer — resolvendo brigas de especificidade

Camadas definem a ordem de prioridade independentemente da especificidade. Uma regra numa camada posterior vence uma regra mais específica de uma camada anterior. É a solução estrutural para o problema que hoje se resolve com !important.

css
@layer base, componentes, utilidades;

@layer base {
  #conteudo p { color: gray; }   /* especificidade alta */
}

@layer utilidades {
  .texto-escuro { color: black; }  /* especificidade baixa... e vence */
}
Cuidado com aninhamento profundo. Aninhar quatro níveis gera seletores enormes e especificidade alta — o mesmo problema que o Sass criou em tanto projeto. Dois níveis costuma ser o limite saudável.

Cores modernas: oklch() e color-mix()

Novo CSS

Hexadecimal não tem lógica interna: #7A1C30 não te diz nada, e “clarear 10%” vira tentativa e erro. O oklch() descreve a cor em três números que fazem sentido — Luminosidade, Croma (saturação) e Hue (matiz, em graus).

css
:root {
  --marca-h: 345;   /* o matiz do marsala, em graus */

  --marca:       oklch(38% 0.13 var(--marca-h));
  --marca-clara: oklch(58% 0.13 var(--marca-h));  /* só a luz mudou */
  --marca-escura:oklch(26% 0.13 var(--marca-h));
}

A vantagem prática: a paleta inteira do cliente sai de um número. Mudou o matiz, mudou tudo de forma coerente — e a diferença de luminosidade é perceptualmente uniforme, coisa que o HSL não garante.

color-mix() — misturar sem calculadora

css
/* a cor da marca com 15% de transparência */
.aviso { background: color-mix(in srgb, var(--marca) 15%, transparent); }

/* a cor da marca puxada para o branco */
.suave  { background: color-mix(in srgb, var(--marca) 20%, white); }
Uso direto no seu trabalho: aquele fundo claro de seção que combina com a cor do cliente. Em vez de pedir o hexadecimal ou chutar no conta-gotas, você deriva do próprio token — e se o cliente trocar a cor, o fundo acompanha.

Métodos de array

Novo JS

São a forma moderna de trabalhar com listas. Em vez de um for com contador, você descreve o que quer.

javascript
const drinks = [
  { nome: "Negroni",  alcool: true,  preco: 32 },
  { nome: "Maracujá", alcool: false, preco: 18 },
  { nome: "Gin Tônica", alcool: true, preco: 28 }
];

// map — transforma cada item, devolve lista do mesmo tamanho
const nomes = drinks.map(d => d.nome);
// ["Negroni", "Maracujá", "Gin Tônica"]

// filter — devolve só os que passam no teste
const semAlcool = drinks.filter(d => !d.alcool);

// find — devolve o PRIMEIRO que bate (ou undefined)
const negroni = drinks.find(d => d.nome === "Negroni");

// reduce — reduz a lista a um único valor
const total = drinks.reduce((soma, d) => soma + d.preco, 0);  // 78

// some / every — devolvem true ou false
const temSemAlcool = drinks.some(d => !d.alcool);   // true
const todosCaros   = drinks.every(d => d.preco > 20); // false

// sort — ordena (cuidado: altera o array original)
const porPreco = [...drinks].sort((a, b) => a.preco - b.preco);

O ganho fica claro quando você encadeia — gerar o HTML da carta de drinks, só os sem álcool, ordenados por preço:

javascript
const html = drinks
  .filter(d => !d.alcool)
  .sort((a, b) => a.preco - b.preco)
  .map(d => `<li>${d.nome} — R$ ${d.preco}</li>`)
  .join('');
Regra para escolher: quer a lista transformada? map. Quer parte da lista? filter. Quer um item? find. Quer um número só? reduce. Quer sim ou não? some ou every.

Destructuring, spread e outros atalhos

Novo JS

Sintaxe que aparece em praticamente todo código dos últimos anos. Saber ler isso é o que separa entender um exemplo da internet de copiar sem saber o que faz.

javascript
// DESTRUCTURING — extrair campos de um objeto
const drink = { nome: "Negroni", preco: 32, alcool: true };

const { nome, preco } = drink;        // cria duas variáveis
const { nome: titulo } = drink;       // renomeando
const { estoque = 0 } = drink;        // valor padrão se não existir

// SPREAD (...) — espalhar o conteúdo
const copia = { ...drink };                    // cópia rasa
const atualizado = { ...drink, preco: 35 };    // cópia com campo trocado
const juntos = [...listaA, ...listaB];         // juntar arrays

// ENCADEAMENTO OPCIONAL (?.) — não quebra se não existir
const cidade = cliente?.endereco?.cidade;   // undefined em vez de erro

// OPERADOR ?? — usa o padrão só quando é null ou undefined
const titulo2 = config.titulo ?? "Sem título";
// (diferente do ||, que também troca string vazia e zero)

// TEMPLATE LITERAL — texto com variáveis e quebras de linha
const msg = `Olá ${nome}, o preço é R$ ${preco}.`;
Diferença que pega muita gente: || considera 0 e "" como “vazio” e troca pelo padrão. O ?? só troca quando é null ou undefined. Num formulário onde zero é resposta válida, essa diferença é bug.

Debounce e throttle

Novo JS

Duas formas de conter eventos que disparam demais. Debounce espera a pessoa parar; throttle executa no máximo a cada X tempo.

javascript
function debounce(fn, espera = 300) {
  let t;
  return function (...args) {
    clearTimeout(t);
    t = setTimeout(() => fn.apply(this, args), espera);
  };
}

function throttle(fn, intervalo = 200) {
  let liberado = true;
  return function (...args) {
    if (!liberado) return;
    liberado = false;
    fn.apply(this, args);
    setTimeout(() => { liberado = true; }, intervalo);
  };
}

// buscar só quando parar de digitar
campo.addEventListener('input', debounce(buscarCep, 500));

// recalcular no máximo 5x por segundo ao redimensionar
window.addEventListener('resize', throttle(ajustarLayout, 200));

PWA e Service Worker

Novo JS

PWA (Progressive Web App) é um site que o celular trata quase como aplicativo: instala na tela inicial, abre sem barra de navegador e funciona offline. São dois ingredientes.

1. O manifesto — dados de instalação

manifest.json
{
  "name": "Art Bar",
  "short_name": "Art Bar",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#0B0B0B",
  "theme_color": "#7A1C30",
  "icons": [
    { "src": "/icone-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icone-512.png", "sizes": "512x512", "type": "image/png" }
  ]
}

2. O service worker — o que faz funcionar offline

É um script que fica entre o site e a internet, interceptando requisições. Ele guarda arquivos e responde com a cópia quando não há conexão.

sw.js
const CACHE = 'artbar-v1';

self.addEventListener('install', (e) => {
  e.waitUntil(
    caches.open(CACHE).then(c => c.addAll(['/', '/index.html']))
  );
});

self.addEventListener('fetch', (e) => {
  e.respondWith(
    caches.match(e.request).then(r => r || fetch(e.request))
  );
});
Antes de vender PWA para um cliente: o service worker guarda versões antigas com muita eficiência. Se você não mudar o nome do cache a cada atualização, o cliente vai continuar vendo o site velho e jurar que você não publicou. É o problema número um de quem começa com PWA.
Vale a pena quando: o site é consultado repetidamente — cardápio, catálogo, área do aluno. Numa landing page que a pessoa visita uma vez e vai pro WhatsApp, não agrega.

Novo

Imagens, na ordem de impacto

DNS é a lista telefônica da internet: traduz o nome do domínio para o endereço do servidor. Quando você aponta um domínio para a Netlify, está editando DNS.

HTTPS é a versão criptografada do protocolo, sinalizada pelo cadeado. Hoje é obrigatório: navegador marca site sem HTTPS como “não seguro” e o Google rebaixa. Nas hospedagens citadas, ele é automático e gratuito — você não precisa comprar certificado.

Segurança

Landing page estática tem pouca superfície de ataque — mas os poucos riscos que existem são exatamente os que passam despercebidos.

XSS — quando texto vira código

Novo JS

XSS (Cross-Site Scripting) acontece quando conteúdo vindo de fora é inserido na página como HTML e o navegador executa. O caminho mais comum é o innerHTML.

o erro
// nome vem da URL: ?nome=<img src=x onerror="alert(1)">
const nome = new URLSearchParams(location.search).get('nome');

saudacao.innerHTML = `Olá, ${nome}!`;   // executa o código do atacante
a correção
saudacao.textContent = `Olá, ${nome}!`;   // insere como texto, não como HTML
Origem do conteúdoPode usar innerHTML?
Escrito por você no códigoSim
Parâmetro da URLNão
Campo de formulárioNão
Resposta de APINão
localStorageNão — o visitante edita
Regra única que basta: textContent por padrão. Só troque por innerHTML quando você mesmo escreveu aquele HTML no código — e nunca com interpolação de dado externo no meio.

Content Security Policy

Novo

Uma declaração que diz ao navegador de onde a página pode carregar coisas. Se um script de outra origem for injetado, o navegador simplesmente recusa.

html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self';
               style-src  'self' 'unsafe-inline' https://fonts.googleapis.com;
               font-src   https://fonts.gstatic.com;
               img-src    'self' data:;
               script-src 'self' 'unsafe-inline'">
Entregando HTML único, existe um conflito: CSP rigoroso bloqueia CSS e JS inline, que é justamente o seu formato. Por isso o exemplo acima usa 'unsafe-inline' — o que enfraquece bastante a proteção. A solução correta é usar nonce, mas isso exige servidor gerando a página. Numa landing page sem dados sensíveis, CSP é ganho pequeno; saber que existe importa mais que aplicar agora.

Outras três precauções

  • rel="noopener" em todo target="_blank". Sem isso, a página aberta consegue manipular a sua pela referência window.opener.
  • Cuidado com script de CDN aleatório. Você está executando código de terceiro na página do seu cliente. Use CDNs conhecidas, com versão fixa — nunca @latest, que muda sem aviso.
  • Nada de .env, backup ou .git na pasta publicada. Se o servidor entrega arquivo estático, ele entrega esses também para quem souber o caminho.
