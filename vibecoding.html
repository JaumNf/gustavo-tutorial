PARTE 1

O mapa das ferramentas

Qual IA serve para quê, quando sair de uma e ir para outra, e por que trocar de ferramenta toda semana custa mais do que parece.

Vibecoding, sem romantizar

Novo

O termo foi popularizado por Andrej Karpathy no começo de 2025: você descreve o que quer, a IA escreve o código, e você julga pelo resultado em vez de ler linha por linha. Funciona — até o dia em que precisa de alguém que entenda o que foi escrito.

A IA faz bemContinua com você
Escrever a primeira versão rápidoDecidir o que construir e para quem
Trocar um layout inteiro em segundosJulgar se ficou bom — e dizer por quê
Lembrar sintaxe e padrões de qualquer linguagemVerificar: abrir, clicar, testar no celular
Explicar o código que ela mesma escreveuProteger chave, banco e dado de quem usa
Seguir um brief bem escritoEscrever o brief
O que separa quem entrega de quem trava não é a ferramenta: é saber pedir (a trilha Trabalhando com IA), saber verificar e saber desfazer. Esta trilha cobre o resto — com o quê trabalhar, onde buscar referência e como não se machucar.

Quatro tipos de ferramenta

Novo

Os nomes mudam todo mês; as categorias, não. Saber em qual categoria está o problema já resolve metade da escolha.

TipoExemplosServe paraNão serve para
ConversaClaude, ChatGPT, Geminipensar, planejar, escrever texto, revisar um trecho, tirar dúvidamanter um projeto de muitos arquivos
Construtor no navegadorLovable, v0, Bolt, Replit, Google AI Studioa primeira versão em minutos, protótipo para mostrar, quem nunca instalou nadacontrole fino, projeto que vai crescer por meses
Agente no códigoClaude Code, Cursor, GitHub Copilot, Codexprojeto de verdade: lê e edita seus arquivos, roda comandos, usa Gitquem ainda não sabe o que é uma pasta de projeto
Mídiageradores de imagem, vídeo e vozassets, ilustração, variação de foto, locuçãofoto do produto real do cliente
Um caminho comum: conversa para planejar e escrever o brief, construtor para ver a ideia de pé, agente para transformar em projeto de verdade. Nem todo projeto precisa das três etapas — site simples pode nascer direto no agente.

Do construtor para o agente: quando sair

Novo

Construtor é ótimo até deixar de ser. Os sinais de que chegou a hora de levar o código para um agente, no seu computador:

  • cada ajuste pequeno custa um pedido inteiro e mexe em coisa que você não pediu
  • você precisa de algo que a plataforma não oferece — outro banco, outra hospedagem, um script próprio
  • o projeto virou coisa séria e precisa de histórico, revisão e backup
  • você quer entender o que está no código, não só o que aparece na tela

Antes de começar num construtor, confira como o código sai de lá: a maioria sincroniza com o GitHub ou deixa baixar o projeto. Se não houver saída, o projeto mora na plataforma — e o dia em que ela mudar de preço ou de regra é o dia em que você recomeça do zero.

Na hora de migrar, o primeiro pedido ao agente não é "continue o projeto": é "leia o projeto e me explique a estrutura em dez linhas". Depois, escreva o arquivo de contexto (veja a parte 3).

Modelo grande, modelo rápido

Novo

Quase toda ferramenta deixa escolher entre um modelo mais capaz e um mais rápido. A regra prática: o grande para decidir, o rápido para executar.

TarefaModelo
Planejar a arquitetura, escolher a estrutura do projetoo mais capaz
Encontrar a causa de um erro difícilo mais capaz
Revisar o que foi feito antes de publicaro mais capaz
Trocar texto, ajustar cor, renomear, repetir um padrão já decididoo rápido
Não escolha modelo por ranking. Teste os dois na sua tarefa: pegue um pedido real que você já fez e compare o resultado. Ranking mede prova genérica; você entrega site.

Uma IA principal, as outras de segunda opinião

Novo

Trocar de ferramenta no meio do projeto quase sempre custa mais do que ganha: o contexto, as decisões e o jeito de pedir ficam para trás. Fique com uma principal — e use as outras como revisoras.

texto
Revise este código como se fosse para produção.
Não reescreva nada. Liste, do mais grave ao menos grave:
erros de lógica, falhas de segurança, o que quebra no celular
e o que vai ser difícil de manter.

[cole o arquivo ou o diff]
Um modelo diferente erra de um jeito diferente — e é por isso que ele enxerga o que o primeiro não viu. A mesma ideia da autocrítica, com um par de olhos novo.
PARTE 2

Referências: onde achar e como usar

A trilha de IA ensina como descrever uma referência. Esta parte ensina onde procurar, como escolher poucas e como desmontar uma antes de pedir.

Onde procurar

Novo

Cada fonte serve a uma pergunta diferente. Procurar "site bonito" no lugar errado rende uma hora de rolagem e nenhuma decisão.

Você querOnde procurar
Clima, cor, composição — o moodboardPinterest
Projeto de design completo — identidade visual, interface, apresentação de caseBehance, Dribbble
Tipografia com efeito, logo, peça gráfica pronta para adaptarKittl
Página inteira de referência — hero, ritmo, seçõesAwwwards, Godly, Land-book, Lapa Ninja, SiteInspire
Tela de aplicativo — cadastro, painel, configuraçõesMobbin
Componente pronto para React e Tailwindshadcn/ui, 21st.dev, Magic UI, Aceternity UI
Componente em HTML e CSS purosuiverse.io, CodePen — e os Modelos deste site
Movimento e efeitomotion.dev (exemplos), Codrops, a vitrine do GSAP
FonteGoogle Fonts, Fontshare
ÍconeLucide, Phosphor, Heroicons
Foto para rascunhoUnsplash, Pexels — e a licença de cada foto antes de publicar

Pinterest, Behance, Dribbble e Kittl mostram design — o clima, a composição, a identidade. Awwwards, Godly e Land-book mostram site funcionando — a rolagem, o ritmo das seções, a interação. Um projeto bom costuma usar os dois: o primeiro para decidir como ele parece, o segundo para decidir como ele se comporta.

Referência do mesmo ramo é a mais perigosa: ela dá a média da categoria. Procure o jeito de organizar em outro ramo — um restaurante com o ritmo de uma revista, um escritório de advocacia com a calma de uma galeria.

Três referências, não trinta

Novo

Trinta prints viram "faça algo moderno". Três prints, cada um com o motivo, viram decisão.

Junte muito, mande pouco. Coletar pode ser à vontade: no Pinterest, uma pasta por projeto, com seções dentro dela — layout, tipografia, cor, foto —, e o Behance e o Kittl para ver identidade e tipografia aplicadas de verdade. Na hora de pedir à IA, saem dali só as três que respondem às perguntas do projeto.

texto
REFERÊNCIAS (anexas)
1. site-a.png — pego o ritmo: seções curtas, muito respiro entre elas
2. site-b.png — pego só a hero: título enorme à esquerda, foto recortada à direita
3. site-c.png — pego os cards de serviço: número grande, uma linha de texto

NÃO pego: as cores de nenhum dos três, nem as fotos.
  • Uma por pergunta: uma para o layout, uma para a tipografia, uma para o movimento.
  • Sempre com o motivo: referência sem motivo vira ordem de cópia.
  • Diga o que não pegar: corta a média das três antes de ela aparecer.
As formas de passar referência — imagem, gravação de tela, descrição de tempo — estão em Formas de referência. Gravação de tela é a única que comunica movimento.

Desmontar a referência antes de pedir

Novo

Antes de mandar o print para a IA, abra a página original e tire as medidas. Com número na mão, o pedido deixa de ser "parecido com isso" e vira especificação.

O que medirOnde, no DevTools
Fonte, peso e tamanho do título e do corposelecionar o texto → aba Computed → font-family, font-size
Cores de fundo, texto e destaqueselecionar o elemento → Styles, ou o conta-gotas do seletor de cor
Espaço entre as seçõesselecionar a seção → a caixa de margem e padding no fim de Computed
Largura máxima do textoselecionar o parágrafo → max-width
A curva e o tempo de uma animaçãoaba Animations — dá para rodar em câmera lenta
O passo a passo do DevTools está na trilha Fluxo de trabalho. Para a paleta e a escala que saíram da medição, as ferramentas Paleta e Escala fecham o sistema.

Inspiração não é cópia

Novo

Estrutura, ritmo e ideia de interação não têm dono. Texto, foto, ilustração, logo e código com licença têm.

Pode pegarNão pode pegar
a ideia de hero dividida em duas colunasa foto da hero
o ritmo de seções curtaso texto das seções
um efeito de rolagem que você reescreveo arquivo de CSS copiado inteiro
a paleta como ponto de partida, ajustadao logo ou algo que confunda as duas marcas
Pedir para a IA "copiar este site" não muda de quem é o conteúdo. O que vale para o que a IA gera está em Direitos.

Biblioteca de componentes: quando vale

Novo

Em projeto React com Tailwind — o que Lovable, v0 e Bolt costumam gerar —, o shadcn/ui virou o ponto de partida mais comum. A diferença para uma biblioteca tradicional: ele copia o código do componente para dentro do seu projeto. O código passa a ser seu; atualização é você quem decide.

bash
# num projeto React + Tailwind já criado
npx shadcn@latest init
npx shadcn@latest add button dialog
SituaçãoCaminho
Projeto React + Tailwind, painel ou appshadcn/ui como base, e os componentes animados por cima
Landing page em HTML puroos Modelos deste site, ou escrever o componente
Precisa de um componente sócopie o componente, não instale a biblioteca inteira
Peça para a IA usar a biblioteca que já está no projeto. Sem essa instrução, ela mistura três jeitos de fazer botão no mesmo site.
PARTE 3

Os recursos dos agentes

Arquivo de contexto, skills, MCP, subagentes, hooks e modo plano: o que cada um resolve e quando vale configurar.

O arquivo de regras de cada ferramenta

Novo

Todo agente lê um arquivo de instruções do projeto antes de começar. É onde moram as decisões travadas, o jeito de entregar e o que não pode ser tocado — o resumo que vira arquivo.

FerramentaArquivo
Claude CodeCLAUDE.md na raiz do projeto
Cursorregras em .cursor/rules/
GitHub Copilot.github/copilot-instructions.md
Codex e outrosAGENTS.md na raiz

O nome e o lugar mudam de versão para versão — confira na documentação da sua ferramenta. O conteúdo é o mesmo em todas, e dá para manter um arquivo só e apontar os outros para ele.

O Gerador de comando monta esse arquivo pelo tipo "Arquivo de contexto", puxando paleta, fontes e escala das outras ferramentas.

Skills: ensinar uma vez, usar sempre

Novo

Uma skill é uma pasta com um arquivo SKILL.md: um nome, uma descrição de quando ela serve, e as instruções. O agente lê só a descrição até precisar; quando a tarefa bate, carrega o resto. É o jeito de ensinar um processo seu — o checklist de entrega, o padrão de commit, o estilo de texto — sem colar tudo em toda conversa.

markdown
---
name: entrega-landing
description: Use antes de entregar uma landing page ao cliente — revisa contraste, 390px, formulário e metadados.
---

# Entrega de landing page

1. Abra a página em 390px e aponte o que estoura na horizontal.
2. Confira contraste 4.5:1 em todo texto.
3. Teste o formulário e o link de WhatsApp.
4. Liste o que faltar como [PENDENTE]. Não corrija sem perguntar.
Onde fica (Claude Code)Vale para
~/.claude/skills/nome/SKILL.mdtodos os seus projetos
.claude/skills/nome/SKILL.mdsó este projeto, e vai junto no Git

Como usar: com a barra, pelo nome

O jeito garantido de usar uma skill é chamá-la: digite / seguido do nome, e o que vier depois vai junto como pedido. A barra também abre a lista das skills instaladas — não precisa decorar os nomes.

texto
/entrega-landing
/entrega-landing só a página de contato
/emil-design-eng revise os botões desta página

Sem a barra, a skill também pode entrar sozinha: quando o pedido bate com a descrição dela, o agente carrega por conta própria. Mas "pode" não é "vai" — para processo que precisa acontecer, chame pelo nome.

A descrição é o que decide quando a skill entra sozinha. "Revisa coisas" nunca é chamada; "use antes de entregar uma landing page" é. Antes de escrever uma, procure uma pronta — há coleções inteiras publicadas —, mas leia antes de instalar: skill é instrução que o agente segue.

MCP: dar mãos para a IA

Novo

O Model Context Protocol é um padrão aberto, lançado pela Anthropic no fim de 2024, para ligar um assistente a outros sistemas: o navegador, o Figma, o GitHub, um banco de dados. Cada ligação é um "servidor MCP" que expõe ferramentas — e o agente passa a poder abrir a página, ler o frame do design ou consultar a tabela sozinho.

bash
# Claude Code: dar ao agente um navegador para abrir e testar a página
claude mcp add playwright -- npx @playwright/mcp@latest

# ver os que estão ligados
claude mcp list
Ligar a…O agente passa a poder
um navegadorabrir a página, clicar, medir e tirar print — verificar sem você
o Figmaler o frame e as variáveis do arquivo em vez de adivinhar pelo print
o GitHubler issues e abrir pull request
um banco de dadosconsultar tabelas — e, se permitir, alterar
Cada servidor é uma porta aberta. Dê o mínimo de acesso: leitura antes de escrita, banco de teste antes do de produção. E conteúdo que o agente lê por MCP — uma página, uma issue — pode trazer instrução escondida; o agente não deve obedecer texto que veio de fora, e você não deve aprovar ação que não pediu.

Comandos, subagentes e hooks

Novo

Três formas de automatizar o que você repete. Nenhuma é obrigatória — comece a usar quando se pegar digitando a mesma coisa pela terceira vez.

RecursoO que éExemplo de uso
Comando próprioum pedido salvo, chamado por nome/revisar roda sempre a mesma revisão de entrega
Subagenteum agente com contexto próprio, chamado pelo principalprocurar em cem arquivos sem encher a conversa principal
Hookum comando que roda sozinho num eventoformatar o código toda vez que um arquivo é editado

No Claude Code, subagentes ficam em .claude/agents/ e hooks nas configurações (settings.json). A diferença que importa: skill e comando são sugestão que o agente segue; hook é regra que o sistema executa — se precisa acontecer sempre, é hook.

Hook roda comando no seu computador sem perguntar. Escreva você, leia antes de salvar, e nunca copie um de fonte que você não conhece.

Modo plano e permissões

Novo

Os agentes deixam escolher quanto de liberdade dar: perguntar antes de cada edição, editar sozinho, ou só planejar sem tocar em nada. O modo plano é o plano antes do código transformado em botão.

SituaçãoModo
Mudança grande, arquitetura, algo que você não sabe como fazerplano: lê, pensa e propõe; você aprova
Tarefa pequena e clara num projeto com Giteditar e mostrar o resultado
Pasta com senha, chave ou dado de clienteperguntar antes de cada comando
Nunca rode um agente sem permissão nenhuma numa pasta que tenha o que perder — arquivo .env, backup, projeto sem commit. A opção existe para ambiente descartável, não para o seu computador de trabalho.
PARTE 4

Quando dá errado

A IA em loop, o erro mal contado, a mudança que ninguém pediu. Como perceber cedo, voltar atrás e seguir.

A IA em loop

Novo

O sinal é sempre o mesmo: o erro volta, a correção desfaz a anterior, e o arquivo cresce a cada pedido. Continuar pedindo "tente de novo" só aprofunda o buraco.

  1. Pare e peça a causa, não a correção: "sem mexer em nada, me diga em uma frase por que isso acontece".
  2. Dê o que falta: a mensagem exata de erro, o passo a passo para reproduzir, o que já foi tentado.
  3. Volte ao último estado bom: desfaça pelo Git e peça de novo, menor.
  4. Recomece a conversa com um resumo curto — o contexto longo é parte do problema.
Três tentativas iguais é o limite. Na quarta, a conversa já está carregando mais erro do que informação — use o tipo "Recomeçar conversa" do Gerador.

Levando o erro certo

Novo

"Não está funcionando" obriga a IA a adivinhar. Um relato bom tem quatro partes e cabe em cinco linhas:

texto
ONDE: o botão "Enviar" do formulário de contato
O QUE ACONTECE: nada; o console mostra
  TypeError: Cannot read properties of null (reading 'value') em form.js:12
COMO REPRODUZIR: Chrome no celular, 390px, preencher e tocar em Enviar
O QUE DEVERIA: abrir o WhatsApp com a mensagem pronta
  • A mensagem do console copiada, não resumida: o arquivo e a linha estão nela.
  • O print quando o problema é visual — com a largura da tela anotada.
  • O que mudou desde a última vez que funcionou.
O tipo "Correção pontual" do Gerador de comando monta esse relato e pede a causa antes da mudança.

Git é o seu botão de desfazer

Novo

Com Git, errar sai barato: cada pedido grande começa de um ponto salvo, e voltar é um comando. Sem Git, a IA pode reescrever o arquivo que funcionava e não existe caminho de volta.

bash
git add -A && git commit -m "antes de refazer o menu"   # salva o ponto

git diff                 # o que a IA mudou desde o último commit
git restore arquivo.css  # desfaz as mudanças de um arquivo
git restore .            # desfaz todas as mudanças ainda não salvas

git log --oneline        # os pontos salvos
git revert HEAD          # desfaz o último commit criando outro — seguro
Commit antes de cada pedido grande, não depois. O passo a passo do Git, do zero, está na trilha Fluxo de trabalho — e o uso junto com agentes em Git com o Claude.

Leia o diff, não a resposta

Novo

A resposta diz "pronto, corrigi". O diff mostra o que de fato mudou — e é onde aparecem os problemas que a resposta não conta.

No diff, desconfie dePorque
arquivo que você não pediu para mexera IA "aproveitou para melhorar" — e pode ter quebrado
teste apagado ou puladoo teste parou de falhar porque sumiu, não porque passou
.env, chave ou configuração de deploy alteradosrisco de segurança e de derrubar o site
dependência nova no package.jsonmais peso, mais coisa para manter — era necessária?
o arquivo inteiro reescrito para uma mudança pequenavariação escondida em partes já aprovadas
Não precisa entender cada linha. Precisa saber onde mexeu e quanto — isso já pega a maior parte dos estragos.

Quando você não entende o código

Novo

Vai acontecer, e não é motivo para aceitar no escuro. Três pedidos resolvem quase sempre:

texto
Explique este arquivo em dez linhas, para quem não programa:
o que ele faz, de onde vêm os dados e para onde vão.

Quais três coisas neste código quebrariam primeiro se
mudássemos de hospedagem ou se dez vezes mais gente usasse?

Me mostre a menor mudança possível para [o que eu quero],
e explique cada linha dela antes de aplicar.
Aprender o básico da camada em que você trabalha paga rápido: a trilha HTML puro cobre o que está por baixo de qualquer framework, e Frameworks explica o que Lovable, v0 e Bolt geram.
PARTE 5

Do protótipo ao ar, sem se machucar

Os erros que mais aparecem em projeto feito com IA: a chave exposta, o banco aberto, a conta que dispara. E o caminho mais curto para publicar.

A chave que vaza

NovoJS

Tudo o que está no JavaScript do navegador é público — qualquer pessoa abre o DevTools e lê. Isso inclui variável de ambiente com prefixo de "pública": VITE_ no Vite e NEXT_PUBLIC_ no Next.js vão parar dentro do arquivo que o visitante baixa.

bash
# .env — nunca vai para o Git
OPENAI_API_KEY=sk-...          # só o servidor lê
VITE_SUPABASE_URL=https://...  # público de propósito
VITE_SUPABASE_ANON_KEY=...     # público de propósito, protegido pelas regras do banco

# .gitignore
.env
.env.local
ChaveOnde pode ficar
Chave secreta de API paga (IA, pagamento, e-mail)só no servidor ou numa função serverless
Chave "anon" / pública de um serviço de bancono front, desde que o banco tenha regras de acesso
Vazou? Revogue e gere outra na hora. Apagar o commit não adianta: o histórico do Git, os clones e os robôs que varrem repositórios já viram. Chave secreta no front é o erro número um de projeto feito com IA — peça sempre "onde fica esta chave?". A função serverless que protege a chave está em Back-end.

Banco aberto: o erro clássico

Novo

No Supabase, a chave pública fica no front por projeto — quem protege os dados são as regras de acesso por linha (Row Level Security). Tabela sem essas regras, com a chave pública à vista, é tabela que qualquer pessoa lê e apaga.

sql
-- liga a proteção: sem regra, ninguém acessa pela chave pública
alter table pedidos enable row level security;

-- cada pessoa lê só os próprios pedidos
create policy "ler os meus pedidos" on pedidos
  for select using (auth.uid() = user_id);

-- e só cria pedido em nome de si mesma
create policy "criar o meu pedido" on pedidos
  for insert with check (auth.uid() = user_id);

No Firebase, o equivalente são as regras de segurança do Firestore — e o "modo de teste", que libera tudo por um tempo, não é para ir ao ar.

Teste como um estranho: abra o site numa aba anônima, sem login, e tente ler e escrever pela chave pública. Se der, o banco está aberto. Peça à IA: "liste as tabelas e as regras de acesso de cada uma".

A conta que dispara

Novo

Serviço cobrado por uso não avisa quando algo dá errado — cobra. Um laço que chama a API sem parar, um formulário sem proteção contra robô, ou uma chave vazada viram fatura.

  • Limite de gasto e alerta no painel de cada serviço pago, antes de ir ao ar.
  • Chamada paga sempre pelo servidor, nunca direto do navegador — e com limite de pedidos por pessoa.
  • Proteção no formulário: um campo-armadilha ou um desafio simples já barra a maior parte dos robôs.
  • Olhe o painel de uso nos primeiros dias depois de publicar.
O formulário com proteção contra robô está em Qualidade; o limite do plano gratuito de cada serviço, em Back-end.

Publicar sem nunca ter aberto um terminal

Novo

O caminho mais curto hoje, e o que a maioria dos construtores e agentes já prepara:

  1. o código num repositório do GitHub (o construtor sincroniza, ou o agente faz o primeiro push);
  2. na Vercel, Netlify ou Cloudflare Pages: "importar projeto do GitHub";
  3. as variáveis de ambiente cadastradas no painel da hospedagem — não no código;
  4. cada push publica sozinho, e cada branch ganha um endereço de prévia para testar antes;
  5. o domínio próprio apontado por último, quando tudo estiver certo.
Hospedagem e domínio em detalhe estão em HTML puro; o Git ligado à Vercel, em Fluxo de trabalho.
