Qualidade

Esta trilha é sobre o que separa uma página que funciona de uma página que funciona bem: o peso da imagem, quem consegue usar, quanto demora para aparecer, e o que se confere antes de mandar o link para o cliente.

PARTE 1

Imagens e mídia

É onde está 80% do peso de uma landing page e a maior parte da diferença entre um site que abre em um segundo e um que abre em oito. Também é onde mora o risco jurídico mais bobo do ofício: usar foto que não é sua.

O que realmente pesa numa página

Novo

Abra a aba Network de qualquer landing page e ordene por tamanho. A ordem é quase sempre a mesma: imagem, imagem, imagem, fonte, JavaScript, CSS, HTML. O HTML — o arquivo que você passou o dia escrevendo — costuma ser o menor de todos.

RecursoPeso típico mal feitoPeso bem feito
Foto de hero3 a 6 MB (direto da câmera ou do celular)80 a 150 KB
Galeria de 8 fotos20 MB500 KB
Fontes400 KB (6 pesos de 2 famílias)60 KB (2 pesos)
HTML da página—30 a 80 KB

A conclusão prática é dura e libertadora: você pode escrever o CSS mais elegante do mundo que não muda nada se a foto da hero tem 4 MB. Otimizar imagem é a única tarefa de performance que vale fazer antes de qualquer outra.

A conta que convence o cliente: 4G brasileiro real entrega algo perto de 2 MB por segundo em condição boa, bem menos em movimento. Uma página de 8 MB leva mais de dez segundos. Metade dos visitantes desiste antes de três.

Qual formato usar

Novo
FormatoUse paraObservação
AVIFFoto, hoje, como primeira escolhaMenor de todos — 30 a 50% abaixo do WebP. Suportado em todos os navegadores atuais.
WebPFoto, como alternativa de segurançaSuporte praticamente universal há anos. Se só puder escolher um, escolha este.
JPGÚltimo fallbackAinda pesa 30% mais que WebP na mesma qualidade.
PNGSó quando precisa de transparência duraPara foto, é o pior dos mundos: enorme. Logo em PNG quase sempre deveria ser SVG.
SVGLogo, ícone, ilustração geométricaEscala em qualquer tela sem perder nitidez e costuma ter poucos KB. É texto — pode editar cor no próprio código.
GIFNuncaPara animação curta, um <video> em MP4 pesa 10 vezes menos.
Regra prática: foto vira AVIF com WebP de reserva. Logo e ícone viram SVG. Se o cliente mandou o logo em JPG com fundo branco, peça o vetor — todo designer que fez aquele logo tem o arquivo .ai ou .svg. Vale insistir: logo pixelado no topo da página é a primeira coisa que derruba a percepção de profissionalismo.

Comprimir — alvos e ferramentas

Novo

Antes de comprimir, redimensione. Uma foto de 6000px de largura numa área que exibe 1200px é desperdício puro, e nenhuma compressão conserta isso.

UsoLargura máximaAlvo de peso
Hero de tela cheia1920px (e uma versão de 960px para celular)até 150 KB
Foto dentro de seção1200pxaté 100 KB
Card / galeria800pxaté 60 KB
Avatar, ícone200pxaté 15 KB

Sem instalar nada: Squoosh (squoosh.app) faz uma imagem por vez mostrando antes e depois lado a lado — bom para calibrar o olho. Qualidade 75 a 80 em AVIF/WebP é indistinguível do original em quase toda foto.

No terminal, para o lote inteiro de uma vez:

terminal
# ImageMagick — redimensiona e converte a pasta toda
magick mogrify -resize 1200x -quality 80 -format webp *.jpg

# Sharp (Node) — mais rápido e melhor qualidade
npx @squoosh/cli --avif '{"quality":75}' --resize '{"width":1200}' fotos/*.jpg

# conferir o resultado
ls -lh *.webp
O hábito que resolve: nenhuma imagem entra no projeto sem passar por isso. Crie a pasta fotos-brutas/ fora do repositório (está no .gitignore), processe de lá para dentro, e o que vai para o Git já está pronto.

srcset e sizes — a imagem certa para cada tela

NovoHTML

Mandar a imagem de 1920px para um celular de 390px é mandar quatro vezes mais pixel do que a tela consegue mostrar. O srcset deixa o navegador escolher.

html
<img
  src="hero-1200.webp"
  srcset="hero-600.webp 600w,
          hero-1200.webp 1200w,
          hero-1920.webp 1920w"
  sizes="(max-width: 700px) 100vw, 1200px"
  width="1200" height="800"
  alt="Sala de estar reformada com marcenaria clara e iluminação embutida"
  fetchpriority="high">

O srcset lista as versões com a largura real em pixels (w). O sizes avisa qual espaço a imagem vai ocupar — é a informação que falta para o navegador decidir, e é o que quase todo mundo esquece de escrever.

Não exagere: três versões cobrem tudo. Gerar sete tamanhos é trabalho que não se paga. E se a imagem sempre aparece pequena — um avatar, um ícone de serviço — uma versão só basta.

Quando carregar — lazy, priority e o pulo do layout

NovoHTML
html
<!-- a imagem da hero: aparece de cara, tem que vir primeiro -->
<img src="hero.webp" width="1200" height="800" alt="..." fetchpriority="high">

<!-- tudo que está abaixo da dobra -->
<img src="obra-3.webp" width="800" height="600" alt="..."
     loading="lazy" decoding="async">
Erro clássico: colocar loading="lazy" na imagem da hero. Ela é justamente a que o navegador deveria buscar primeiro — atrasá-la piora diretamente a nota de LCP. Lazy é para o que está fora da tela, e só.

E o width com height em toda imagem: sem eles, o navegador não sabe quanto espaço reservar, a página monta, a imagem chega e tudo pula para baixo. É o CLS — a métrica que mede exatamente esse salto. Os dois números não precisam ser o tamanho final na tela; precisam ser a proporção correta, e o CSS cuida do resto:

css
img { max-width: 100%; height: auto; display: block; }

/* quando a área tem tamanho fixo e a foto precisa preencher */
.card__foto { aspect-ratio: 4 / 3; object-fit: cover; }

<picture> — formato moderno com reserva

NovoHTML

O navegador lê os <source> de cima para baixo e usa o primeiro que entende. O <img> no final é obrigatório e é o que sempre funciona.

html
<picture>
  <source srcset="hero.avif" type="image/avif">
  <source srcset="hero.webp" type="image/webp">
  <img src="hero.jpg" width="1200" height="800" alt="..." fetchpriority="high">
</picture>

<!-- e o outro uso: foto DIFERENTE por tamanho de tela -->
<picture>
  <source media="(max-width: 700px)" srcset="hero-vertical.webp">
  <img src="hero-horizontal.webp" width="1600" height="900" alt="...">
</picture>
Esse segundo caso é art direction, e resolve um problema real: a foto panorâmica que funciona no desktop vira uma faixa ilegível no celular. Em vez de espremer, você troca por um recorte vertical da mesma cena.

De onde vem a foto — e o risco real

Novo

Pegar imagem no Google e colocar no site do cliente é a prática mais comum e mais arriscada do mercado. Existem empresas que fazem busca reversa automatizada e cobram — a cobrança chega para o cliente, e a conversa sobre quem colocou aquilo ali chega para você.

FontePode usar comercialmente?Atenção
Unsplash, Pexels, PixabaySim, gratuitoSem exclusividade — o concorrente pode usar a mesma. Cuidado com foto que tem rosto identificável ou marca visível.
Bancos pagos (Shutterstock, Adobe Stock)Sim, conforme a licença compradaA licença costuma ser por projeto. Guarde o comprovante.
Google ImagensNãoBuscador não é banco de imagem. "Estava na internet" não é licença.
Instagram do clienteDependeSe o cliente tirou, sim. Se foi fotógrafo contratado, o direito costuma ser do fotógrafo — pergunte.
Imagem gerada por IAEm geral simRegras mudam por ferramenta e por país. Nunca use para simular obra que o cliente não fez.
A regra ética que vale mais que a jurídica: foto de banco em site de serviço é provisória, para o cliente ver o layout. Obra de arquitetura que não é do arquiteto, prato que não é do restaurante, sala que não é da clínica — isso é o visitante sendo enganado. Combine desde o orçamento: as fotos definitivas são responsabilidade do cliente, e entram antes de publicar.

Favicon e imagem de compartilhamento

NovoHTML

Duas imagens que ninguém lembra e que aparecem em todo lugar: o ícone da aba e a miniatura que aparece quando o link é colado no WhatsApp.

no head
<link rel="icon" href="/favicon.svg" type="image/svg+xml">
<link rel="icon" href="/favicon.ico" sizes="32x32">
<link rel="apple-touch-icon" href="/apple-touch-icon.png"><!-- 180x180 -->

<meta property="og:title" content="Vanessa Carvalho · Arquitetura em Campo Grande">
<meta property="og:description" content="Projetos de interiores e reforma de apartamento, do projeto à entrega.">
<meta property="og:image" content="https://site.com.br/og.jpg"><!-- 1200x630 -->
<meta property="og:url" content="https://site.com.br/">
<meta name="twitter:card" content="summary_large_image">
Três detalhes que quebram na prática: a og:image precisa de URL absoluta (com https://), precisa ser JPG ou PNG — WhatsApp e Facebook ainda engasgam com WebP —, e precisa pesar menos de 300 KB. Teste colando o link no seu próprio WhatsApp antes de entregar; se a miniatura não aparecer, o cliente vai notar antes de você.
PARTE 2

Acessibilidade

Um site acessível é um site que funciona para quem não enxerga bem, não usa mouse, não ouve, ou está com o braço quebrado. No Brasil também é lei. E, para o seu trabalho, é o argumento de venda que nenhum concorrente de orçamento está usando.

Por que importa — inclusive juridicamente

Novo

Cerca de um quarto da população brasileira declara algum tipo de deficiência, e a maior parte é visual. Some quem tem 60 anos e presbiopia, quem está no sol com o brilho baixo, quem quebrou o braço direito. Acessibilidade não é caso de nicho — é o caso comum em condição ruim.

O lado legal: a Lei Brasileira de Inclusão (13.146/2015) determina que sites de empresas com sede ou representação comercial no país sejam acessíveis. Para órgãos públicos existe o eMAG, que é obrigatório. O padrão técnico que todo mundo usa como referência é o WCAG, nível AA.

Como isso vira venda: na proposta, "o site é entregue com acessibilidade conforme WCAG AA, atendendo à Lei Brasileira de Inclusão" é uma linha que o concorrente que cobra R$ 400 não escreve. Para cliente que é clínica, escritório de advocacia ou qualquer negócio que atende idoso, isso pesa — e o custo para você é quase zero se for feito desde o começo.

Semântica: o HTML certo já é metade do caminho

RevisãoHTML

Leitor de tela navega pela estrutura, não pela aparência. Se a estrutura existe, ele funciona sozinho. Se tudo é <div>, ele lê uma sopa sem começo nem fim.

html
<!-- inacessível: o leitor de tela não sabe o que é nada disso -->
<div class="topo"><div class="menu">...</div></div>
<div class="titulo-grande">Arquitetura em Campo Grande</div>
<div class="botao" onclick="abrir()">Orçamento</div>

<!-- acessível: mesma aparência, estrutura declarada -->
<header><nav aria-label="Principal">...</nav></header>
<main>
  <h1>Arquitetura em Campo Grande</h1>
  <button type="button">Orçamento</button>
</main>
<footer>...</footer>

A hierarquia de títulos é a outra metade: um <h1> por página, e nada de pular de h2 para h4 porque ficou do tamanho certo. Tamanho é trabalho do CSS; o número do título é informação de estrutura.

Div com onclick é o pecado mais comum. Um <button> de verdade já recebe foco pelo Tab, já dispara com Enter e Espaço, e já se anuncia como botão. Refazer tudo isso na mão com ARIA dá dez linhas — usar a tag certa dá zero.

Teclado e foco visível

NovoCSS

Teste de trinta segundos que revela quase tudo: abra sua página e navegue só com Tab. Você deveria conseguir chegar em todo link, todo botão e todo campo, sempre vendo onde está.

css
/* NUNCA faça isso — é o crime número um de acessibilidade */
*:focus { outline: none; }

/* faça isso: um foco visível que combina com o site */
:focus-visible {
  outline: 3px solid var(--accent);
  outline-offset: 2px;
  border-radius: 2px;
}

/* e o pulo do gato para site com cabeçalho fixo */
html { scroll-padding-top: 90px; }

:focus-visible é a solução do dilema antigo: ele mostra o contorno para quem navega por teclado e não mostra para quem clicou com o mouse. Era exatamente isso que as pessoas tentavam resolver apagando o outline.

Link de pular para o conteúdo: quem usa teclado tem que passar pelos dez itens do menu em toda página. Um link escondido, que aparece ao receber foco, resolve — e leva quatro linhas de CSS:
html + css
<a class="pular" href="#conteudo">Pular para o conteúdo</a>

.pular { position:absolute; left:-9999px; }
.pular:focus { left:8px; top:8px; z-index:999; background:#fff;
               padding:10px 14px; border:2px solid currentColor; }

Texto alternativo que serve para alguma coisa

Novo

A regra é uma pergunta: se eu tivesse que ler esta página por telefone para alguém, o que eu diria sobre esta imagem?

html
<!-- inútil -->
<img src="img1.jpg" alt="imagem">
<img src="img1.jpg" alt="foto reforma apartamento campo grande arquitetura">

<!-- útil -->
<img src="sala.jpg" alt="Sala integrada com cozinha, marcenaria clara e
     bancada de madeira maciça separando os ambientes">

<!-- decorativa: alt vazio, de propósito -->
<img src="textura.svg" alt="">

<!-- imagem que É um link -->
<a href="/"><img src="logo.svg" alt="Vanessa Carvalho, página inicial"></a>
SituaçãoO que escrever
Foto que informaDescreva o que importa na foto, em uma frase
Decoração puraalt="" — vazio, mas presente. Sem o atributo, o leitor lê o nome do arquivo.
LogoO nome da empresa
Ícone ao lado de textoalt="" — o texto já diz
Imagem com texto dentroTranscreva o texto. Melhor ainda: não coloque texto dentro de imagem.
Não comece com "imagem de" ou "foto de" — o leitor de tela já anuncia que é uma imagem. E não repita a legenda que está logo abaixo: a pessoa ouve duas vezes.

Contraste medido, não achado

NovoCSS

Cinza claro sobre branco é a assinatura visual do site que ninguém consegue ler no celular no sol. O padrão WCAG AA tem números:

ElementoContraste mínimo
Texto normal4.5:1
Texto grande (24px, ou 19px em negrito)3:1
Borda de campo, ícone que informa3:1
Texto sobre foto4.5:1 — contra a parte mais clara da foto

Onde medir: as próprias DevTools mostram a razão ao clicar no quadradinho de cor no painel Styles, com um aviso quando reprova. Para conferir uma paleta inteira, o WebAIM Contrast Checker.

css
/* texto sobre foto: nunca confie na foto */
.hero { position: relative; }
.hero::after {
  content: ""; position: absolute; inset: 0;
  background: linear-gradient(to top, rgba(0,0,0,.65), rgba(0,0,0,.15));
}
.hero__texto { position: relative; z-index: 1; color: #fff; }
E o detalhe que quase todo site erra: placeholder de campo em cinza claro. Ele é texto, precisa dos mesmos 4.5:1 — e, mesmo legível, placeholder não substitui <label>, porque some assim que a pessoa começa a digitar.

ARIA — e quando não usar

NovoHTML

A primeira regra oficial do ARIA é: não use ARIA. Se existe um elemento HTML que faz aquilo, use o elemento. ARIA só descreve — não adiciona comportamento nenhum.

html
<!-- errado: parece botão, mas não recebe Tab nem responde a Enter -->
<div role="button" onclick="enviar()">Enviar</div>

<!-- certo -->
<button type="button" onclick="enviar()">Enviar</button>

Os poucos atributos que você realmente vai usar em site de serviço:

html
<!-- botão sem texto visível -->
<button aria-label="Abrir menu"><svg aria-hidden="true">...</svg></button>

<!-- diferenciar navs quando há mais de uma -->
<nav aria-label="Principal">  <nav aria-label="Rodapé">

<!-- estado que muda -->
<button aria-expanded="false" aria-controls="painel">Dúvidas</button>

<!-- decoração que o leitor deve ignorar -->
<span aria-hidden="true">→</span>

<!-- mensagem que aparece depois e precisa ser anunciada -->
<p role="status">Mensagem enviada.</p>
ARIA errado é pior que ARIA nenhum. Um aria-expanded="false" que nunca vira true faz o leitor de tela anunciar o oposto do que está acontecendo. Se você não vai manter o atributo sincronizado no JavaScript, não o coloque.

PARTE 3

Performance medida

Performance não é sensação, é três números que o Google publica e usa para ranquear. Saber o nome de cada um e o que conserta cada um transforma "o site está lento" em uma lista de tarefas.

Core Web Vitals — os três números

Novo
MétricaMedeBomRuim
LCP
Largest Contentful Paint		Quando a maior coisa da tela terminou de aparecer — geralmente a foto ou o título da heroaté 2,5sacima de 4s
INP
Interaction to Next Paint		Quanto a página demora para responder a um clique ou toqueaté 200msacima de 500ms
CLS
Cumulative Layout Shift		Quanto a página pula sozinha enquanto carregaaté 0,1acima de 0,25

Traduzindo para o que o visitante sente: LCP é "demorou para aparecer", INP é "travou quando cliquei", CLS é "eu ia clicar e o botão fugiu".

O INP substituiu o antigo FID em 2024 e é bem mais exigente, porque mede todas as interações da visita, não só a primeira. Em site de HTML puro ele costuma estar ótimo sem esforço nenhum — é uma vantagem sua que vale citar em proposta.

Consertar o LCP

Novo

Primeiro descubra qual elemento é o LCP: rode o Lighthouse e ele aponta na seção de diagnóstico. Em landing page é quase sempre a foto da hero ou o <h1>.

html
<!-- 1. avise o navegador antes mesmo de ele achar a imagem -->
<link rel="preload" as="image" href="hero.webp" fetchpriority="high">

<!-- 2. nunca lazy na hero, sempre prioridade alta -->
<img src="hero.webp" fetchpriority="high" width="1200" height="800" alt="...">

<!-- 3. conexão antecipada com o que vem de fora -->
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
CausaConserto
Imagem da hero pesadaComprimir e servir AVIF/WebP — resolve a maioria dos casos sozinho
Imagem com loading="lazy"Tirar o lazy da hero
Fonte bloqueando o textofont-display: swap e preload da fonte principal
CSS gigante no caminho críticoEm HTML único isso não existe; em site com muitos CSS, carregar o resto depois
Servidor lentoHospedagem com CDN. Vercel, Netlify e Cloudflare Pages resolvem de graça.

Consertar o CLS

NovoCSS

CLS é o mais fácil de zerar e o mais irritante para quem visita. Quatro causas cobrem praticamente todos os casos.

css
/* 1. imagem sem dimensão → sempre width e height no HTML */
img, video { max-width: 100%; height: auto; }

/* 2. área que recebe conteúdo depois → reserve o espaço antes */
.mapa { aspect-ratio: 16 / 9; }
.depoimentos { min-height: 320px; }

/* 3. fonte que troca e muda a altura do texto */
@font-face {
  font-family: 'Bricolage';
  src: url(...) format('woff2');
  font-display: swap;
  size-adjust: 100%;      /* ajuste fino para a fonte de reserva ocupar o mesmo espaço */
}

/* 4. banner/aviso que empurra a página → sobreponha, não empurre */
.aviso-cookie { position: fixed; bottom: 0; left: 0; right: 0; }
Como ver o pulo acontecendo: DevTools → Performance → grave o carregamento com throttling ligado. A linha "Layout Shift" marca cada salto, e clicando nela o navegador mostra qual elemento se mexeu.

Consertar o INP

NovoJS

INP ruim quer dizer uma coisa só: tem JavaScript demais ocupando a única linha de execução que o navegador tem. Enquanto uma função roda, nada responde.

js
// 1. scripts de terceiro NUNCA bloqueando
<script src="analytics.js" defer></script>

// 2. evento que dispara muito precisa de freio
window.addEventListener('scroll', debounce(minhaFuncao, 100), { passive: true });

// 3. trabalho pesado sai do caminho da interação
btn.addEventListener('click', () => {
  mostrarResultado();                    // o que o usuário precisa ver AGORA
  requestIdleCallback(() => registrar()); // o resto espera a folga
});

// 4. animar só transform e opacity — o resto força recálculo de layout
O maior vilão em site de cliente costuma ser terceiro: pixel do Meta, chat de atendimento, mapa do Google embutido, widget de avaliação. Cada um traz o próprio JavaScript. Meça antes e depois de adicionar cada um — e leve o número para a conversa quando o cliente pedir o quinto widget.

Fontes — o gargalo que ninguém vê

NovoCSS

Fonte externa é o segundo maior peso depois de imagem, e afeta LCP e CLS ao mesmo tempo. Três decisões resolvem.

Menos pesos. Duas famílias, dois ou três pesos cada. Seis pesos de duas famílias são uns 400 KB por nada — o olho não distingue 300 de 400 no corpo de texto.

Sempre font-display: swap. Sem ele, o navegador esconde o texto por até três segundos esperando a fonte chegar. O visitante olha uma tela em branco enquanto o texto existe e está pronto.

Considere hospedar você mesmo. Baixar o .woff2 e servir do próprio domínio elimina uma conexão externa, e ainda ajuda na conversa de LGPD — o Google Fonts registra o IP de quem visita.

css
@font-face {
  font-family: 'Inter';
  src: url('/fontes/inter-400.woff2') format('woff2');
  font-weight: 400;
  font-display: swap;
  unicode-range: U+0000-00FF, U+0131, U+0152-0153;  /* só latim — corta metade do arquivo */
}
A opção de custo zero: a pilha de fontes do sistema. font-family: system-ui, -apple-system, 'Segoe UI', Roboto, sans-serif carrega instantaneamente porque já está no aparelho, e fica nativa em cada sistema. Para site de serviço onde a tipografia não é o argumento, é uma escolha defensável — e o LCP agradece.

Máscara de telefone e CPF

NovoJS

Sem biblioteca, sem dependência. A ideia é sempre a mesma: tira tudo que não é dígito, limita o tamanho, e reinsere os separadores.

js
function mascaraTelefone(v) {
  v = v.replace(/\D/g, '').slice(0, 11);
  if (v.length <= 10) return v.replace(/(\d{0,2})(\d{0,4})(\d{0,4})/,
      (_, a, b, c) => (a ? '(' + a : '') + (b ? ') ' + b : '') + (c ? '-' + c : ''));
  return v.replace(/(\d{2})(\d{5})(\d{0,4})/, '($1) $2-$3');
}

function mascaraCPF(v) {
  return v.replace(/\D/g, '').slice(0, 11)
          .replace(/(\d{3})(\d)/, '$1.$2')
          .replace(/(\d{3})(\d)/, '$1.$2')
          .replace(/(\d{3})(\d{1,2})$/, '$1-$2');
}

document.querySelector('#fone').addEventListener('input', (e) => {
  e.target.value = mascaraTelefone(e.target.value);
});
Validar CPF é diferente de mascarar. O CPF tem dígito verificador; 111.111.111-11 passa na máscara e não existe. Só valide de verdade se o negócio precisa — para formulário de contato de arquiteta, pedir CPF já é pedir demais, e cada campo a mais derruba a conversão.

CEP que preenche o endereço

NovoJS

O ViaCEP é gratuito, não exige cadastro nem chave, e economiza quatro campos de digitação no celular.

js
const cep = document.querySelector('#cep');

cep.addEventListener('blur', async () => {
  const valor = cep.value.replace(/\D/g, '');
  if (valor.length !== 8) return;

  try {
    const r = await fetch(`https://viacep.com.br/ws/${valor}/json/`);
    const d = await r.json();
    if (d.erro) { avisar('CEP não encontrado'); return; }

    document.querySelector('#rua').value    = d.logradouro;
    document.querySelector('#bairro').value = d.bairro;
    document.querySelector('#cidade').value = d.localidade;
    document.querySelector('#uf').value     = d.uf;
    document.querySelector('#numero').focus();   // manda o foco para o que falta
  } catch {
    avisar('Não consegui buscar o CEP. Preencha o endereço manualmente.');
  }
});
Duas coisas que separam o bom do ruim aqui: sempre deixe os campos editáveis (CEP de rua nova vem errado ou vazio) e sempre tenha o caminho manual quando a consulta falhar. API de terceiro cai, e o formulário não pode cair junto.

Como apresentar para o cliente aprovar

Novo

Mandar o link e escrever "pronto, dá uma olhada" é o caminho mais curto para dez mensagens de ajuste desconexas ao longo de três semanas.

Mande a URL de pré-visualização, não a de produção. Com o repositório ligado à Vercel, um branch já vira um endereço próprio — o cliente vê sem que nada esteja no ar de verdade.

Diga o que você quer que ele olhe. "Confere por favor: o telefone, os três serviços, e se o texto da hero está do jeito que você fala com seu cliente. O restante ainda vou ajustar." Sem isso, ele comenta a cor do botão e não percebe que o telefone está errado.

Peça para abrir no celular dele. É onde o cliente dele vai ver, e é onde aparece o que você não testou.

Combine quantas rodadas de ajuste estão incluídas. Duas é o padrão razoável. Isso é conversa de contrato — e está na trilha Negócio.

E registre a aprovação por escrito, mesmo que seja uma mensagem de WhatsApp dizendo "pode publicar". É o que separa "ajuste combinado" de "trabalho novo" três semanas depois.
